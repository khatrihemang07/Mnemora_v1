# Search matching lives in core, and Todo's keys are one pure reducer

The Journal's search rules (word prefixes, case and accents ignored, quoted phrases, typo tolerance as a separate "similar" group, no FTS syntax ever reaching the index) are also Todo's. Modules never import each other, so the parts that are not about one Module's tables moved to `mnemora_core::search`: query parsing into a safe FTS5 expression, bounded edit distance and near words, folding, plain reading text from Markdown, and marking matches in spans. Each Module keeps its own index and SQL (Todo's are `todo_tasks_fts` over title and notes and `todo_comments_fts`, with an `fts5vocab` table each for typos). A Task matches when its title and notes match or one of its live Comments does; deleted rows stay indexed, so Undo works, and every query filters on `deleted_at`. Results are open Tasks first in manual order, then Done and Won't do ones, latest closed first, each with its title cut into matched and plain spans and, when the match is in the notes or a Comment, that one line as a snippet. The browser mock reuses the Journal mock's TypeScript copy of the same rules, and one JSON fixture (`todo-search-rules.json`) runs against both.

The desktop key map is the second decision. Todo's keys (the ring, Space, ⇧Space, Enter, E, D, T, M, 1–4, ⌥↑↓, ⌫, Esc, ⌘F, the sheet's ⌘↑↓ and ⌘↵, and the G chords) had grown one handler at a time. They are now one pure function, `reduceKey(state, event, scene, now)`, that returns an action; the page builds the scene (typing, overlay, sheet, which Task is meant, whether the key went to a button), runs the action, and owns every side effect. The only state is when G was pressed. Every row of the map and every refusal (typing, menu open, modifiers, repeats) is a Vitest case, and the guard is the one from ADR 0011.

Every Task key acts on the focused Task only. v1 let E, D, T, M, 1–4, ⇧Space and ⌥↑↓ also act on the row under the pointer; that was dropped in v1.1, because a key meant for the row the user is looking at could land on whichever row the pointer happened to rest on (after scrolling, for one). The scene therefore knows only the ring or no target.

## Considered Options

- **Copy the Journal's matching into the Todo crate**: rejected; two copies of a tolerance rule drift apart, and the user expects one behaviour.
- **Todo depends on the Journal crate**: rejected; Modules never import each other (ADR 0002).
- **Keep a handler per key family**: rejected; the guards (typing, overlays, the sheet, hover versus ring) were being re-derived in each, and a bug such as Space acting on a hovered row could hide in one of them.
- **Hide Done Tasks from search behind a toggle**: rejected (prototype S3); they are most of what people look for later, so they come after the open ones.
