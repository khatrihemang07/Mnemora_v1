# App-wide Change Log in Core

Core keeps one `change_log` table that any Module writes to when an entity changes. Each record holds the full JSON snapshot of the entity after the change, with its Module, entity kind, entity id, operation and timestamp. Changes made within one editing session carry a session id and replace that session's single record, so many autosaves become one record; a session that created the entity stays recorded as a `create`. Operations are `create`, `update`, `move`, `tick`, `delete` and `restore`. Records for live entities are kept forever and purged together with an entity when it is deleted for good (the Journal purges 30 days after deletion). The raw log never crosses IPC, but a Module may read its own records to build a view: Todo's Task History (see the amendment below). It is also the basis for sync.

## Considered Options

- **Diffs**: rejected; they are small but cannot be read, restored or merged without replaying the chain, and one lost record corrupts everything after it.
- **Metadata only** (who, what, when): rejected; it cannot restore content or feed a sync.
- **Per-Module history tables**: rejected; every Module would reimplement session batching and purging, and sync would have to know each table. One core table keeps that in one place.

## Amendment: the change log is readable over IPC through History

The Task sheet's History fold is built from this log, so it is no longer internal. Core gains `changelog::read(entity, entity_id)`, which returns one entity's records oldest first. The Todo crate turns consecutive snapshots into readable lines in Rust (`crates/todo/src/history.rs`, command `todo_task_history`): "Due date Thu 22 Oct → Fri 23 Oct", "Priority P4 → P1", "Moved 📥 Inbox → 💼 Work", "Done (occurrence of 18 Oct)", "Created", "Title edited". Only these lines cross IPC, never snapshots, and the lines carry dates, list names and Priorities but never the Task's own text.

Batching is what the editing session was for: the Task sheet sends one session id per opening, so every autosave of the title and notes replaces one record. A session's record carries the latest snapshot and moves to the end of the log whenever it is rewritten, so other changes made during the opening (a Priority, a date) can sit before it and already contain some of its text. History therefore never compares text with the neighbouring record: it keeps a baseline of the title and notes as they were settled before the session (at creation, after an earlier session, or after a Checklist reset on completion) and compares the session's final text with that. One opening is exactly one "Title edited" and one "Notes edited" line, however much else happened in between. Task snapshots leave out derived fields (the Comment count). A Skip on a repeating Task is a `tick` whose snapshot also carries `skipped: true`: a tick that only moves the Due date would otherwise read as completing an occurrence, so History reads the marker and writes "Skipped (Thu → Sat)" (whole dates when the two days are a week or more apart). Undoing a skip puts the date back with an ordinary `update`, which reads as a Due date line. The Todo Module purges deleted Tasks, Lists and Comments after 30 days at startup, together with their records, as the Journal does. (Superseded: see the amendment below, which removes the purge.)

## Amendment (2026-10-22): no purge, and the log carries device, clock and sequence for sync

Sync (ADR 0017) needs the log forever, so the purge above is removed. Journal Entries and Todo Tasks, Lists and Comments that are deleted stay hidden for good and act as their own tombstones, and so do their records; the 30-day purge at startup is gone. The log is kept forever because text is merged by replaying it (see `prev` below).

The log gains four things, recorded on every write, including the in-place rewrite of an editing session's record: the origin device id, a hybrid logical clock (milliseconds and a counter, ties broken by device id) and a local monotonic sequence. Records received from other devices are stored with their origin device and origin sequence, which is how a device knows what it has already seen. Every syncable mutation is now recorded and bumps `updated_at`, including a Comment's soft delete and moving Comments between a Task and its occurrence, and every Preference write is a record of entity `setting` with id `module.key`, including the "save if unset" path.

The fourth is `prev` (core migration 6): for each field a record changed, the value it replaced on its author's device. Text is not newest-wins. Sync replays every stored record of a text unit (an Entry's body, a Task's title or notes, a Comment) in clock order, and a record whose `prev` differs from the replayed text is merged three-way against that `prev`, the newer record winning a clash. The result is a pure function of the records, so the order they arrive in cannot matter. Records from before `prev` existed have none and simply replace. A local table (`sync_text_replay`) memoises the replay so a long Entry is not replayed whole for every record.

History reads in the order (clock milliseconds, clock counter, device id) instead of by record id, so every device shows the same story.

## Amendment (2026-10-24): rows the log never described join it before Sync reads it

Sync sends the log, not the tables, so a row with no records (made before an entity or field was logged, by an older version, or around the log) would never reach another device, while the first-merge preview, which counts rows, promised it would. Before Sync first reads the log after it is switched on, and before the preview counts, each Module's `backfill_log` compares every row with its entity's latest snapshot (`changelog::backfill`): a row with no record gets a `create`, a row that differs gets an `update` of the differing fields, a row that matches gets nothing, so it is deterministic and idempotent. Deleted rows are included. The records are stamped with the row's own `updated_at`, raised so that clock order stays sequence order within the device (the engine counts on it), after the entity's newest record and after what the row refers to (a Task's List, a Comment's Task, an occurrence's Task), and the device clock is shown the stamp so later real changes sort after. Task History is built from the same records, so a row that had none now reads "Created" at its `updated_at`; rows that were fully logged get nothing.
